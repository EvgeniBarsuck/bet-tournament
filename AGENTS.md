# Работа с репозиторием

NestJS-сервис: HTTP и RabbitMQ consumer в одном процессе, PostgreSQL — источник истины. Node.js 24+, TypeScript strict, npm. Задание и запуск описаны в README.md, принятые допущения — в DECISIONS.md.

## Структура

- `src/bets/` — схема события (Zod), `BetsService` (правила начисления и отмены, границы транзакций), `BetsRepository` (весь SQL по ставкам и счетам), `BetsConsumer` (разбор сообщения, ACK, DLQ, requeue, остановка).
- `src/leaderboard/` — `LeaderboardRepository` (SQL рейтинга), `LeaderboardService`, HTTP-контроллер.
- `src/config/` — разбор окружения (`loadConfig`) и глобальный `ConfigModule` с токеном `CONFIG`.
- `src/db/` — пул `pg`, `transaction()`, `isReady()` (последняя миграция применена), `retry.ts` (классификация временных ошибок и повтор целой транзакции), раннер миграций.
- `src/messaging/` — `topology.ts` (quorum-очередь, DLX, классическая DLQ), `republish.ts` (копия сообщения с подтверждением брокера), `BrokerStatus` (подключён ли консьюмер).
- `src/health.controller.ts` — `/health/live` и `/health/ready`; статусы ответов — в `src/health.constants.ts`.
- `src/common/` — общее для нескольких модулей: форматы ID, валюты и сумм (`formats.ts`), декоратор `@PlayerId()`. Сюда — только то, что используют минимум два модуля или что относится к HTTP-контракту в целом.
- `migrations/` — SQL. Применённые миграции не редактировать, добавлять новый файл: `/health/ready` ждёт последнюю из них.
- `scripts/` — продюсер (фиксированные сценарии и `load` с ожидаемыми очками), миграции, smoke.
- `test/unit/` — валидация, конфиг, retry, статус брокера, поведение consumer на подставном канале.
- `test/integration/` — настоящая PostgreSQL: начисления, отмены, гонки, миграции, лидерборд, HTTP и health.
- `.github/workflows/ci.yml` — те же проверки в CI.

SQL — в репозитории, бизнес-правила — в сервисе. Значения с договорным смыслом (статусы, pattern, имена очередей, коды ошибок, таймауты, лимиты, значения по умолчанию, форматы) хранить в `*.constants.ts` рядом с владельцем или в `src/common/formats.ts`, если они общие; литералами в коде их не писать. SQL, тексты ошибок и пути маршрутов остаются на месте. Не добавлять generic-репозитории, дополнительные слои, CQRS и новые хранилища без конкретного требования.

`return` — короткий, в одну строку. Объект или массив сначала собрать в именованную переменную, тело транзакции вынести в отдельный метод (`BetsService.settleIn`), а не писать коллбэк внутри `return`; для промиса с коллбэком — `Promise.withResolvers()`. Проверка: `grep -rnE '^[[:space:]]*return[^;]*$' src scripts test` ничего не находит.

## Ошибки

| Категория | Чем бросать | Обработка |
| --- | --- | --- |
| Бизнес-отказ: невалидное событие, конфликт владельца или полей, неизвестная валюта | `BetRejectedError` с кодом из `BET_REJECTION` | копия в DLQ с `x-rejection-code`, `warn` с кодом, без retry |
| Временная ошибка БД: deadlock, lock timeout, обрыв соединения, недоступный хост | родная ошибка `pg`, не оборачивать | повтор всей транзакции, затем копия в конец очереди; в DLQ не отправлять |
| Невозможное состояние (баг) | обычный `Error` | копия в DLQ с кодом `UNEXPECTED_ERROR`, `error` со стектрейсом |
| Невалидный конфиг при старте | `Error` / `ZodError` | процесс падает |
| HTTP-граница | исключения Nest (`BadRequestException` и т.п.) | статус ответа; в сервисах не использовать |

Новый вид бизнес-отказа — новый код в `BET_REJECTION`, а не новый класс ошибки.

## Инварианты

1. Деньги и очки — десятичные строки и `NUMERIC`; арифметика выполняется в SQL, JS `number` для денег не используется. Очки целые: `floor` на каждой ставке при начислении.
2. Ставка и счёт игрока меняются в одной транзакции. Счёт меняется атомарной дельтой (`points = points + $1`), а не через чтение и запись в JS.
3. ACK — только после commit, no-op или подтверждённой брокером публикации копии (в DLQ или в очередь). Auto-ack не включать.
4. Отмена списывает сохранённое `bets.points`, а не пересчёт по текущему курсу или полям события.
5. Отмена окончательна: поздний settled после отмены ничего не начисляет.
6. Владелец ставки проверяется до no-op; чужой `playerId` — конфликт.
7. Повторяются только временные ошибки БД (`isTransientDbError`); ошибки данных сразу уходят в DLQ. Временная ошибка никогда не отправляет сообщение в DLQ: авария БД не должна выкидывать данные. Возвращать сообщение в очередь публикацией копии, а не `nack` с requeue: `nack` расходует `x-delivery-limit` quorum-очереди. `nack` с requeue — только запасной путь, если брокер не принял копию: неподтверждённое сообщение на живом канале занимает слот `PREFETCH` до `consumer_timeout`.
8. Топ и позиция игрока считаются одним SQL-запросом. Порядок: очки DESC, `player_id` ASC (collation C), нулевые счета исключены.
9. Записи `bets` не удалять: на них держится идемпотентность.
10. При остановке (`beforeApplicationShutdown`) сначала отменяется подписка (`basic.cancel` по `CONSUMER_TAG`), затем прерываются повторы, затем консьюмер ждёт, пока каждое доставленное сообщение будет подтверждено или возвращено копией. Не оставлять сообщения неподтверждёнными до закрытия канала: это расходует `x-delivery-limit`.
11. Аргументы очереди (`queueOptions`) менять только вместе с инструкцией по пересозданию очереди в README: RabbitMQ отказывает в `assertQueue` с другими аргументами.
12. Канал amqplib закрывать раньше соединения (`withChannel`): закрытие одного соединения теряет отправленные `ack`.

## Проверки

```sh
npm run check                                  # prettier, eslint, build, unit
docker compose up -d --wait postgres rabbitmq
npm run test:integration
docker compose up --build -d --wait app
npm run test:smoke
```

Нужен `.env` из `.env.example`; его читают npm-скрипты флагом `--env-file-if-exists` (без `dotenv`), поэтому запускать через `npm run`. Тесты запускаются из `dist`, поэтому после изменений нужна сборка. Integration работает только с базой, имя которой оканчивается на `_test`, во временной схеме. При изменении `BetsService`, `BetsRepository`, SQL или миграций запускать integration; при изменении consumer, `main.ts` или Compose — ещё и smoke. Блокировки не подменять моками и не ослаблять тесты ради зелёного прогона.

ESLint (`eslint.config.mjs`) проверяет:
- type-aware набор `recommendedTypeChecked`, в том числе потерянные Promise;
- `return await` внутри `try`, иначе `catch` и `finally` не поймают ошибку;
- границы модулей: `bets/` и `leaderboard/` не импортируют друг друга, а `common/`, `config/`, `db/` и `messaging/` не импортируют ни один из них;
- `console` в `src/` запрещён, нужно использовать Nest `Logger`; в `scripts/` и `test/` разрешён;
- `eqeqeq`, порядок импортов (`simple-import-sort`), пустые строки между логическими шагами.

Порядок импортов и пустые строки исправляет `npx eslint . --fix`. Не включать `consistent-type-imports`: `import type` у классов, которые внедряются через DI, убирает метаданные Nest и ломает приложение в рантайме.

Особенность Nest: для `@EventPattern` нужна форма `@EventPattern<string>(...)`, иначе strict-сборка не проходит из-за перегрузки декоратора. `enableShutdownHooks` вызывать с `useProcessExit: true`: в контейнере Node — PID 1, и повторно поднятый Nest сигнал игнорируется.

Не коммитить `.env`, `node_modules`, `dist`.
